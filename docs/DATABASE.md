# Database

PostgreSQL 17. Four tables: `jobs`, `admin_users`, `sessions`,
`schema_migrations`. Accessed through `pgx/v5` with hand-written,
`$n`-parameterised SQL and no ORM ([D-6](DECISIONS.md#d-6--pgxv5-and-hand-written-sql-no-orm)).

The migration files in `backend/migrations/` are the authoritative definition of
the schema. This document explains the design and the reasoning; where a column
name or a constraint here disagrees with `001_init.sql`, the SQL is right and
this file is the bug.

## 1. Conventions

| Convention | Rule | Why |
|---|---|---|
| Primary keys | `uuid`, generated application-side as UUID v4 | A UUID can be generated before the insert, which keeps the service layer free of a round trip. It also means an id in a URL or a log leaks no row count |
| Timestamps | **`timestamptz` everywhere. Never `timestamp`.** | `timestamp` (without time zone) stores a wall-clock reading with no anchor. Two servers in different zones write "14:00" meaning different instants and nothing detects it. `timestamptz` stores an instant |
| Time zone | Everything is written and read as **UTC**, serialised RFC 3339 with a `Z`. Humanising happens at render time in the browser | An international job board has users in every zone. There is exactly one correct answer to "when was this published", and it is an instant, not a local reading |
| `now()` | Defaults and mutations use `now()` in SQL rather than a client-supplied time | The database clock is the single clock. A client with a skewed clock cannot write a job published in the future |
| Enumerated values | **`text` with a `CHECK` constraint**, never a Postgres `enum` type | See [section 3](#3-status-lifecycle) |
| Booleans | `boolean NOT NULL DEFAULT false` where the absence of a value means "no"; nullable only where "unknown" is genuinely different from "no" | |
| Free text | `text`, not `varchar(n)`. Length limits are enforced in `backend/internal/validation` against the contract | In Postgres `text` and `varchar(n)` have identical performance. A length limit in the schema requires a migration to change and produces a database error rather than a per-field `VALIDATION_FAILED` with a useful message |
| Naming | `snake_case`, singular column names, plural table names | Matches the JSON field names in the contract, so no mapping layer is needed |
| Deletion | Soft, via `deleted_at` ([D-18](DECISIONS.md#d-18--soft-delete-rather-than-hard-delete)) | |

## 2. `jobs`

The seven required fields from the product requirement, the columns needed to
run the site, and a set of nullable, future-ready columns so the roadmap needs no
rewrite.

| Column | Type | Null | Default | Purpose |
|---|---|---|---|---|
| `id` | `uuid` | no | — | Primary key. UUID v4, generated by the application. Used in **admin** URLs |
| `slug` | `text` | no | — | URL-safe identifier. Used in **public** URLs, never `id`. Unique among non-deleted rows — see [section 5](#5-slug-uniqueness). Derived from `title` by the rules in contract section 8 |
| `title` | `text` | no | — | Required. 3–160 chars after trim |
| `description` | `text` | no | — | Required. 20–20,000 chars. **Plain text with newlines, not HTML.** Renderers must escape it |
| `salary` | `text` | no | — | Required. Free text, 1–120 chars — `"$140k – $175k"`, `"Competitive"`, `"€60,000/yr"`. Deliberately not numeric: an international board sees currencies, ranges, equity and hourly rates, and a numeric column would force every one of those into a lie |
| `qualification` | `text` | no | — | Required. Free text, 1–240 chars |
| `job_type` | `text` | no | — | Required. `CHECK` against `full-time \| part-time \| contract \| internship \| freelance \| temporary` |
| `location` | `text` | no | — | Required. Free text, 1–160 chars, e.g. `"Berlin, Germany"` |
| `apply_url` | `text` | no | — | Required. The exact URL the administrator supplied, stored and returned byte-for-byte. Validated on write **and** re-checked on render — see [SECURITY.md](SECURITY.md#2-the-apply_url-allowlist) |
| `status` | `text` | no | `'draft'` | `CHECK` against `draft \| published \| unpublished`. See [section 3](#3-status-lifecycle) |
| `company` | `text` | **yes** | `null` | Employer name. Nullable because a listing may be posted without one |
| `country` | `text` | **yes** | `null` | Separate from `location` so it can be filtered exactly while `location` stays human-readable |
| `remote_type` | `text` | **yes** | `null` | `CHECK` against `remote \| hybrid \| onsite` when not null |
| `experience_level` | `text` | **yes** | `null` | Free text, e.g. `"5+ years"`. Free text rather than an enum because the vocabulary is not agreed yet; promoting it to a checked set later is additive |
| `category` | `text` | **yes** | `null` | Free text for now. A real taxonomy would want its own table |
| `is_featured` | `boolean` | no | `false` | First term in the public ordering. Not null because "unknown" is meaningless here |
| `expires_at` | `timestamptz` | **yes** | `null` | When set and in the past, the job stops being publicly visible **with no scheduled job involved** — expiry is part of the read predicate, so it takes effect the moment the clock passes it |
| `published_at` | `timestamptz` | **yes** | `null` | Set on first publish and **never rewritten** on a re-publish. Second term in the public ordering |
| `view_count` | `bigint` | no | `0` | For later analytics. Not written by anything today. See [ARCHITECTURE.md](ARCHITECTURE.md#9-extension-points) for why incrementing it is not free |
| `apply_click_count` | `bigint` | no | `0` | Same |
| `deleted_at` | `timestamptz` | **yes** | `null` | Soft delete. Non-null means gone everywhere. See [Soft delete](#soft-delete) |
| `created_at` | `timestamptz` | no | `now()` | Final ordering tiebreak, which is what makes the public ordering total and therefore stable across pages |
| `updated_at` | `timestamptz` | no | `now()` | Touched on every mutation. Primary ordering for the admin list |

Every one of the nullable, future-ready columns is either nullable or has a
default. That is the whole reason they exist now rather than later: **adding a
nullable or defaulted column to a live table is a metadata-only operation, while
adding a required column is a migration with a data-backfill problem attached.**
Deciding on `remote_type` today costs nothing; deciding on it after 5,000 rows
exist costs a backfill and a decision about what the old rows mean.

## 3. Status lifecycle

```
                    POST /api/admin/jobs
                    (status omitted, or "draft")
                              |
                              v
                        +-----------+
              +-------->|   draft   |
              |         +-----------+
              |               |
              |               | POST .../publish
              |               | status  = 'published'
              |               | published_at = COALESCE(published_at, now())
              |               v
              |         +-----------+
              |         | published |  <-- the ONLY status the public API returns
              |         +-----------+
              |               |
              | POST          | POST .../unpublish
              | .../publish   | status = 'unpublished'
              | (again)       | published_at unchanged
              |               v
              |         +-------------+
              +---------| unpublished |
                        +-------------+

  From any state:  DELETE .../{id}  ->  deleted_at = now()
                   (the status is left alone; deleted_at is the terminal flag)
```

| Transition | Effect on `published_at` |
|---|---|
| `draft` -> `published` (first time) | Set to `now()` |
| `published` -> `unpublished` | **Unchanged** |
| `unpublished` -> `published` | **Unchanged** — `COALESCE(published_at, now())` keeps the original |

The `COALESCE` is the entire rule, and it exists because `published_at` drives
the public ordering. Rewriting it on a re-publish would send a three-month-old
job to the top of the list because someone corrected a typo, unpublished, and
republished. The date a job was first made public is a fact about the job, not a
record of the last time anyone touched it — `updated_at` is that.

`PUT` may also change `status` directly, but the publish and unpublish endpoints
are the preferred path precisely because they carry these semantics.

### Why `CHECK`-constrained `text` and not a Postgres `enum`

Adding a state — `scheduled`, say — is:

```sql
-- text + CHECK: one statement, no type change, no rewrite
ALTER TABLE jobs DROP CONSTRAINT jobs_status_check;
ALTER TABLE jobs ADD CONSTRAINT jobs_status_check
  CHECK (status IN ('draft', 'published', 'unpublished', 'scheduled'));
```

With a Postgres `enum` the equivalent is a change to a **type** that other
objects depend on. `ALTER TYPE ... ADD VALUE` exists and is cheap, but it
historically could not run inside a transaction block alongside other statements
(which conflicts with the one-migration-one-transaction rule in
[Migrations](#migrations)), and **removing or renaming a value is genuinely
painful**: create a new type, alter every dependent column, drop the old type,
in order, on a live table.

What an `enum` would have been better at: it is more compact on disk, comparisons
are on an integer rather than a string, and it gives you an ordering for free.
None of those matter at this scale — the table has a handful of distinct status
values and thousands, not billions, of rows — whereas schema flexibility matters
on the first day someone asks for scheduled publishing.

`job_type` and `remote_type` follow the same pattern for the same reason, and the
contract already tells clients to tolerate an unknown enum member by displaying
it verbatim. That is what makes adding a member a non-breaking change end to
end.

## 4. The public visibility predicate

Quoted once, and once only:

```sql
status = 'published' AND deleted_at IS NULL AND (expires_at IS NULL OR expires_at > now())
```

Three conditions, three distinct ways a job stops being public:

| Condition | Excludes |
|---|---|
| `status = 'published'` | Drafts and anything unpublished |
| `deleted_at IS NULL` | Soft-deleted rows |
| `expires_at IS NULL OR expires_at > now()` | Expired listings. A null `expires_at` means "never expires", so the common case needs no value |

**It lives in SQL, inside the repository layer, and is part of every public
query.** Not in a handler, not in a service helper, not in a shared Go function
that a handler must remember to call. The reason is a failure mode, not
tidiness: if the predicate were applied above the query, then "the handler forgot
it" becomes possible, and the resulting bug leaks unpublished job content while
every existing test still passes. Nothing in the type system would flag it and
no error would be logged. Baking it into the SQL means the query that returns a
draft **does not exist** in the codebase, which is a much stronger guarantee than
a code-review convention.

Consequences that follow, and are all desirable:

- Expiry needs no scheduler, no cron and no background worker. A job expires at
  the instant the clock passes `expires_at`, on the next read.
- The public detail endpoint cannot distinguish "no such slug" from "exists but
  not visible": both produce zero rows, so both are `404 JOB_NOT_FOUND`. That is
  the contract's deliberate behaviour, and here it is a property of the query
  rather than a rule someone has to enforce.
- The admin list uses a different, explicit predicate (all statuses, expiry
  ignored, deleted excluded unless asked for). Two predicates, each in one place,
  and no shared "flags" parameter that could be passed wrongly.

## 5. Slug uniqueness

```sql
CREATE UNIQUE INDEX jobs_slug_unique_active
  ON jobs (slug)
  WHERE deleted_at IS NULL;
```

Note the `WHERE`. This is a **partial** unique index, and the partiality is the
point.

A plain `UNIQUE (slug)` constraint would mean a soft-deleted job **permanently
reserves its slug**. Delete `senior-cloud-engineer` by mistake on Monday, try to
recreate it on Tuesday, and you get `409 SLUG_CONFLICT` pointing at a row nobody
can see, in a UI with no way to inspect or release it. The workarounds are all
bad: rename the deleted row's slug on delete (mutating data on the way out, and
destroying the ability to restore it cleanly), hard-delete instead (losing the
recovery that soft delete exists for), or accept `senior-cloud-engineer-2` as
the permanent URL for the replacement (a worse URL, forever, because of a
deleted row).

The partial index makes the rule say what was actually meant: **a slug is unique
among jobs that exist.** A soft-deleted row keeps its slug — which matters, since
restoring it should restore its URL — but stops competing for it.

The trade-off, stated honestly: two rows can hold the same slug if one is
deleted, so any query joining or looking up by slug **must** include
`deleted_at IS NULL` or it can match more than one row. Every public query
already does, via the visibility predicate. A future admin lookup by slug must
remember to. That is the price of the partial index and it is worth paying.

De-duplication on write (contract section 8) checks against non-deleted rows and
appends `-2`, `-3` and so on, so an auto-derived slug never returns `409`. Only
an explicitly supplied slug can conflict.

Reserved slugs — `new`, `admin`, `api`, `jobs`, `login`, `logout`, `health`,
`ready`, `sitemap`, `robots` — are enforced in application validation, not in the
database. They exist to stop a job URL colliding with a route, which is a
routing concern the database has no knowledge of.

## Soft delete

`DELETE /api/admin/jobs/{id}` sets `deleted_at = now()`. The row is never
removed.

| Behaviour | Detail |
|---|---|
| Public visibility | Gone immediately — `deleted_at IS NULL` is in the visibility predicate |
| Admin list | Excluded by default; `GET /api/admin/jobs?include_deleted=true` shows them |
| Slug | Retained by the row, but released for reuse by the partial index |
| Deleting twice | `404 JOB_NOT_FOUND` — an already-deleted job is not found |
| `status` | Left untouched. `deleted_at` is the terminal flag, and preserving the old status means a restore comes back as what it was |

### Recovering a row

There is deliberately **no restore endpoint**. Recovery is a manual database
operation, which is the right friction level for something that should be rare
and deliberate:

```sql
-- 1. Find it. Search by slug or title; the row is still there.
SELECT id, slug, title, status, deleted_at
FROM jobs
WHERE deleted_at IS NOT NULL
  AND slug = 'senior-cloud-engineer';

-- 2. Check nothing living has taken the slug in the meantime.
SELECT id, slug FROM jobs
WHERE slug = 'senior-cloud-engineer' AND deleted_at IS NULL;

-- 3. If step 2 returned nothing, restore.
UPDATE jobs
SET deleted_at = NULL, updated_at = now()
WHERE id = 'THE-UUID-FROM-STEP-1';
```

**Step 2 is not optional.** If a live job now holds that slug, step 3 violates
`jobs_slug_unique_active` and fails — which is the index doing its job. Give the
restored row a new slug, and accept that its old public URL now belongs to
something else.

### Why soft delete at all

See [D-18](DECISIONS.md#d-18--soft-delete-rather-than-hard-delete) for the full
reasoning. The short version: a job posting is content someone spent time
writing, deletion is one click in a UI, and `DELETE` on a live database is not
undoable. The cost is that every query must filter on `deleted_at`, which is
real and is exactly the kind of thing people forget — which is why the filter is
in the predicate rather than in a convention.

Purging genuinely old deleted rows (a `DELETE FROM jobs WHERE deleted_at <
now() - interval '1 year'`) is a reasonable future addition. Nothing does it
today, so the table grows monotonically. At this scale that is not a problem for
a very long time.

## 7. `admin_users`

| Column | Type | Null | Default | Purpose |
|---|---|---|---|---|
| `id` | `uuid` | no | — | Primary key |
| `email` | `text` | no | — | Login identifier. Unique, case-insensitively — see below |
| `name` | `text` | no | — | Display name. Returned by `/api/admin/me` |
| `password_hash` | `text` | no | — | **Argon2id, PHC-encoded.** Never returned in any response, ever. Parameters travel inside the string, so they can be upgraded without invalidating old hashes — see [SECURITY.md](SECURITY.md#5-password-storage) |
| `last_login_at` | `timestamptz` | yes | `null` | Set on successful login. Returned in the `Admin` shape, so an unexpected value is visible to the account owner |
| `created_at` | `timestamptz` | no | `now()` | |
| `updated_at` | `timestamptz` | no | `now()` | |

Email uniqueness is enforced on the **lowercased** value:

```sql
CREATE UNIQUE INDEX admin_users_email_unique ON admin_users (lower(email));
```

Case-insensitive because `Admin@example.com` and `admin@example.com` are the same
mailbox in every mail system anyone uses, and two accounts differing only in case
is a support incident waiting to happen. The lookup on login must use the same
`lower(email)` expression, or it will not use this index.

Rows are created **only** by `backend/cmd/adminctl`, which has no HTTP surface.
There is no registration endpoint and no role column: every row in this table is
a full administrator. That is a deliberate simplification for a single-operator
product, and it is the thing that must change first if employer accounts are ever
added — a role column plus per-row ownership on `jobs`, which is why that
extension is described as substantial rather than nearly done.

## 8. `sessions`

Server-side sessions, so revocation is a `DELETE`
([D-19](DECISIONS.md#d-19--sessions-in-postgres-rather-than-a-jwt)).

The exact column names are fixed by `backend/migrations/001_init.sql`. The design
the contract requires is:

| Concept | Type | Purpose |
|---|---|---|
| Primary key | `uuid` | Row identity. **Not** the session token, and never sent to a client |
| Token hash | `text` or `bytea`, **unique** | **`sha256(token)` only.** The plaintext 32-byte token exists in the login response and the browser's cookie jar and nowhere else. A database dump yields no usable session because there is nothing to reverse |
| CSRF token | `text` | The value the client must echo in `X-CSRF-Token`, compared in constant time |
| Admin user | `uuid`, FK to `admin_users(id)`, `ON DELETE CASCADE` | Deleting an admin must invalidate their sessions. Cascade makes that impossible to forget |
| Created at | `timestamptz` | Anchor for the **absolute** 7-day expiry |
| Last seen at | `timestamptz` | Anchor for the **idle** 12-hour expiry; touched as the session is used |
| Expires at | `timestamptz` | The absolute deadline, so expiry is a comparison rather than an arithmetic expression at read time |

Both expiries are checked **server-side on every request**. The cookie's
`Max-Age` is a convenience for the browser and is never the authority — a client
that edits or ignores it gains nothing.

Login **replaces** the row rather than adding one, which is the
anti-session-fixation control: a token an attacker planted before login is
worthless after it.

Expired rows are not self-removing. Cleaning them up is a periodic
`DELETE FROM sessions WHERE expires_at < now()` — the rows are already refused
by the middleware, so this is housekeeping rather than a security control, and
it is not automated today.

## 9. `schema_migrations`

| Column | Type | Purpose |
|---|---|---|
| `version` | `text`, primary key | The migration filename or its numeric prefix. A text key means `001_init` sorts and reads naturally and needs no parsing |
| `applied_at` | `timestamptz` | When it ran. Cheap, and the first thing you want during an incident |

This table is written only by the migration runner. Never edit it by hand. The
one exception, done knowingly: marking a migration as applied when the change was
already made out of band — and if you are doing that, write down why somewhere
permanent.

```sql
SELECT version, applied_at FROM schema_migrations ORDER BY version;
```

## Indexes

Every index below exists to serve a specific query. An index with no query is
write amplification with extra steps.

| Index | Columns | Query it serves |
|---|---|---|
| `jobs_pkey` | `jobs (id)` | `GET /api/admin/jobs/{id}`, and every admin update, publish, unpublish and delete |
| `jobs_slug_unique_active` | `jobs (slug) WHERE deleted_at IS NULL` | `GET /api/jobs/{slug}` — the hottest public lookup — and it enforces slug uniqueness among live rows. See [section 5](#5-slug-uniqueness) |
| `jobs_public_list` | `jobs (is_featured DESC, published_at DESC, created_at DESC) WHERE status = 'published' AND deleted_at IS NULL` | `GET /api/jobs`. Column order matches the contract's ordering exactly, so the sort is satisfied by the index. Partial, so it indexes only the rows the public list can ever return — which on a board with many drafts and expired listings is a fraction of the table |
| `jobs_admin_list` | `jobs (updated_at DESC)` | `GET /api/admin/jobs`, whose ordering is `updated_at DESC` |
| `jobs_expires_at` | `jobs (expires_at) WHERE expires_at IS NOT NULL` | The expiry half of the visibility predicate, and any "expiring soon" view. Partial because the common case is `null` and there is no reason to index it |
| `jobs_country` | `jobs (lower(country))` | The `country` filter, which is an exact case-insensitive match. The expression must match the query's expression or the index is not used |
| `jobs_job_type` | `jobs (job_type)` | The `job_type` filter |
| `admin_users_email_unique` | `admin_users (lower(email))` | Login lookup, and case-insensitive uniqueness |
| `sessions_token_hash_unique` | `sessions (token_hash)` | Session validation — this runs on **every** admin request, so it must be an index lookup and nothing else |
| `sessions_admin_user_id` | `sessions (admin_user_id)` | "Sign this admin out everywhere", and the cascade on admin delete |
| `sessions_expires_at` | `sessions (expires_at)` | The expired-session sweep |

### What is deliberately not indexed

**Free-text search (`q`) has no index.** It is a case-insensitive substring match
across `title`, `company`, `location` and `description`, which in SQL is
`ILIKE '%term%'`. A leading wildcard cannot use a btree index, so this is a
sequential scan, and adding a btree on those columns would be an index that
never gets used.

That is the correct answer for now — a table with thousands of rows scans in
single-digit milliseconds, and there is no search UI wired up yet. The additive
fix, when there is:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX jobs_search_trgm ON jobs
  USING gin ((title || ' ' || coalesce(company,'') || ' ' || location || ' ' || description) gin_trgm_ops);
```

A trigram GIN index does serve `ILIKE '%term%'`. The alternative is a `tsvector`
column with a GIN index, which gives better relevance ranking and stemming but
does not do substring matching — so it changes the search *semantics*, not just
its speed. Pick deliberately when the time comes; both are additive migrations
and neither is needed today.

`view_count` and `apply_click_count` are unindexed because nothing reads them yet.

## Migrations

### The mechanism

| Property | Detail |
|---|---|
| Format | Plain `.sql` files in `backend/migrations/`, embedded into the binary with `embed.FS` |
| Naming | Sequential numeric prefix: `001_init.sql`, `002_indexes.sql`, `003_...`. Applied in filename order |
| Runner | About sixty lines in `backend/internal/database` ([D-7](DECISIONS.md#d-7--plain-sql-files-and-an-embedded-runner)) |
| Direction | **Forward only.** There are no `down` migrations |
| Transaction | Each file runs inside **one** transaction. A failing file leaves nothing behind |
| Concurrency | A **Postgres advisory lock** is taken before anything is applied |
| Idempotence | Files already listed in `schema_migrations` are skipped, so running it twice is a no-op |
| Invocation | `adminctl migrate` (the production path — see [DEPLOYMENT.md](DEPLOYMENT.md#33-migrations-are-a-deliberate-action-never-a-cold-start)), `scripts/migrate.sh` / `scripts/migrate.ps1` locally, or `RUN_MIGRATIONS_ON_START=true` at boot (correct for local development, **wrong for serverless production**) |

### Why the advisory lock matters

Any host can start several instances simultaneously — a deploy, or a traffic
spike after idle — and on a serverless host the instance count is not something
the application sets at all. If each ran the migrations, two instances could read
"003 is not applied", and both apply it. For `CREATE INDEX` that is a duplicate-object
error and a crash-looping container; for a data migration it is the same change
applied twice, which may not be detectable afterwards.

`pg_advisory_lock` on a fixed key serialises this without any coordination
between instances: the first instance holds the lock and migrates, the others
block, and when they acquire it they find everything applied and skip. This is
the difference between "migrations on start" being safe and being a race you find
out about during a deploy.

### Why forward-only

A `down` migration is a promise that the reverse of a change is well-defined. It
usually is not. `DROP COLUMN` cannot be undone by `ADD COLUMN` — the data is
gone. A `down` that recreates the column and leaves it null is not a rollback,
it is a differently-broken state that a test suite will happily pass.

So instead: to reverse a change, **write a new forward migration**. The history
stays append-only and always describes what actually happened. And because
production rollback of a schema is not available, non-additive changes are done
in stages — add the new thing, deploy code that tolerates both, migrate the data,
then remove the old thing in a later release. That is slower and it is the only
approach where a code rollback does not require a schema rollback. See
[DEPLOYMENT.md](DEPLOYMENT.md#13-health-readiness-and-rollback).

### Rules

1. **A production schema is never hand-edited.** Not with `psql`, not in a
   dashboard SQL editor, not "just this once for an incident". A hand-edited
   schema is a schema no migration file describes, so the next deployment's
   migration runs against a database nobody has a definition for. If an incident
   truly demands an out-of-band change, write the migration file immediately
   afterwards and record that it was applied by hand.
2. **Never edit an applied migration file.** Environments that already ran it
   will not run it again, so the file and the database silently diverge — and the
   divergence appears only on the next fresh database, usually in CI, as a
   failure nobody can reproduce locally. Add a new file.
3. **Additive by default.** New columns are nullable or defaulted. A `NOT NULL`
   column with no default fails against any existing row.
4. **One logical change per file.** Debugging a failed migration is much easier
   when the file does one thing.
5. **Migrate through the direct connection string, not the pooled one.** DDL in a
   transaction plus an advisory lock both need session affinity, which a
   transaction-mode pooler does not guarantee. See
   [DEPLOYMENT.md](DEPLOYMENT.md#32-two-connection-strings-and-which-goes-where).
6. **Snapshot before anything destructive.** Neon's branching makes a
   pre-migration branch cheap. An untested restore is not a backup.

### Checking state

```sql
SELECT version, applied_at FROM schema_migrations ORDER BY version;
```

Compare against `ls backend/migrations/`. Anything in the directory and not in
the table is pending.

## 12. Future migrations

The roadmap, mapped onto concrete additive changes. Each is one migration file
and none requires a rewrite of anything above — which was the point of adding the
nullable columns on day one.

| Feature | Migration | Notes |
|---|---|---|
| Search at scale | `CREATE EXTENSION pg_trgm` + a GIN index | See [Indexes](#indexes). Purely an index addition — no schema change, no API change |
| Scheduled publishing | Widen the `status` `CHECK` to include `scheduled`, add `publish_at timestamptz` | Additive. The visibility predicate already excludes anything that is not `published`, so a `scheduled` row is invisible from the moment it exists. Then something must promote due rows — a small periodic job, which is the first background process this system would own |
| A real category taxonomy | New `categories` table, plus `category_id uuid REFERENCES categories(id)` on `jobs` | Keep the existing `category` text column during the transition, backfill, then drop it in a **later** release. Two migrations and a deploy in between, not one big one |
| Employer accounts | `employers` table; `employer_id uuid` on `jobs`, nullable at first; a role column on `admin_users` | The schema part is easy. The hard part is per-row authorisation in the repository layer, and it is why this is listed as substantial in [ARCHITECTURE.md](ARCHITECTURE.md#9-extension-points) |
| Job seeker accounts, saved jobs | `users`, `saved_jobs (user_id, job_id)` with a composite primary key | Entirely new surface: registration, email verification, password reset. The `sessions` design is reusable but its assumptions (a handful of admins) are not |
| Job alerts | `alert_subscriptions` (email, query criteria, cadence, verification token) | Needs a scheduler and an email provider. The first genuinely stateful addition |
| Analytics | Nothing new — `view_count` and `apply_click_count` already exist | The question is not schema but write strategy: a counter update on every page view defeats edge caching and puts a write in the read path. Batch it, sample it, or move it to a separate endpoint called after render |
| Application tracking | `applications` table | Only if applying ever happens **on** Job Paglu. Today `apply_url` sends the visitor to the employer, by design, and that is a product decision rather than a technical gap |
| Audit log | `admin_audit_log` (actor, action, target, before, after, at, request id, ip), append-only | Flagged in [SECURITY.md](SECURITY.md#why-the-audit-log-is-the-most-valuable-next-addition) as the most valuable next security addition. Additive, no dependency, and the service layer already has every value it needs at the moment of each mutation |
| Purging old deleted rows | A periodic `DELETE FROM jobs WHERE deleted_at < now() - interval '1 year'` | Policy, not schema. Decide the retention period deliberately and write it down before automating it |
